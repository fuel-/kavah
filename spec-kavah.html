API Design

Base URL

https://api.kavah.app/v1

Auth Strategy

Magic Link Flow:

  1. User submits email → API generates a secure random token, stores HMAC-SHA256 hash in Redis with 15-min TTL
  2. SendGrid sends email with sign-in link containing the raw token
  3. User clicks link → API validates token, issues session cookie (HttpOnly, Secure, SameSite=Lax)
  4. Session ID stored in Redis with 30-day TTL, rotated on each use

Admin Auth: Separate /admin/login with email + password (bcrypt, cost 12). Short-lived session, IP-pinned.

S3 Key Structure

verses/{verse_id}/audio_manual.mp3   ← manually uploaded override

All S3 objects are private. Users always access audio via signed CloudFront URLs — never direct S3 URLs.

CMS Architecture

The admin CMS is a route group (/admin/*) within the same Go binary. Protected by a separate admin session, never exposed to public users.

ElevenLabs Integration Notes

  • Voice ID is configured via environment variable — changing voices requires no code changes
  • Concurrent request limit respected via a Go semaphore
  • Audio stored immediately on generation — no re-generation on playback
  • If generation fails, admin is notified and can retry or upload manually

Phase 2 Architecture Considerations

Phase 1 backend is designed to carry forward into the Phase 2 native app without rebuilding. Decisions baked in now:

  • REST API is versioned (/v1/) — Phase 2 React Native app consumes the same endpoints
  • Auth can extend to Apple Sign-In / Google OAuth without breaking existing magic link sessions
  • play_event.source field supports web, ios, android tracking from day one
  • Stripe Payment Intents are compatible with the data model when Apple IAP / Google Play Billing replaces them in Phase 2
  • Push notification preferences table is pre-modeled but not activated in Phase 1

Security

Authentication

  • Magic link tokens: cryptographically random (32 bytes), HMAC-SHA256 hashed before Redis storage
  • Session cookies: HttpOnly, Secure, SameSite=Lax, 30-day rolling expiry
  • Admin passwords: bcrypt cost factor 12
  • Rate limiting on auth endpoints: 5 attempts per IP per 15 minutes (Redis-backed)

Audio Access

  • All audio served via signed CloudFront URLs (15-min TTL)
  • URLs are optionally IP-bound (configurable — trade-off with mobile network switching)
  • S3 bucket is fully private — no public access policy

Stripe Webhook Security

  • Webhook endpoint validates Stripe-Signature header using secret key
  • Idempotency: stripe_payment_intent_id is unique-indexed — duplicate webhook events are safe

Dependency Security

  • govulncheck runs in CI on every push
  • Dependencies pinned with go.sum

Privacy & GDPR Notes

  • Account deletion: soft-delete via deleted_at, then hard-delete PII on a 30-day background job
  • Data export: GET /account/export returns JSON of all user data
  • Waitlist entries stored with explicit consent timestamp
  • PostHog configured to respect Do Not Track header; no PII sent to PostHog

Scale Migration Path (DigitalOcean → AWS)

Everything is Docker-first. If Phase 2 usage warrants migration:

  1. Go app containers → AWS ECS Fargate (no code changes)
  2. Managed PostgreSQL → AWS RDS (pg_dump/restore, connection string swap)
  3. Managed Redis → AWS ElastiCache (connection string swap)
  4. S3 + CloudFront — already on AWS, no migration needed
  5. Load balancer → AWS ALB

CI/CD Pipeline

Push to main:
  1. go test ./...
  2. govulncheck ./...
  3. docker build
  4. docker push  (GitHub Container Registry)
  5. DigitalOcean App Platform deploy  (rolling, zero-downtime)

Feature branches: run tests only. No deploy.

Open Questions

These items need client resolution before or during development:

  1. NKJV API vendor — which specific licensed API are you using for the NKJV text? (e.g., API.Bible with NKJV license, Faithlife, direct Thomas Nelson license + self-hosted data?) This affects the Bible integration architecture.
  2. ElevenLabs plan — which plan and which voice has been selected? Concurrent generation limits vary by plan and affect CMS performance.
  3. Audio coverage — will every verse in the curated library have ElevenLabs-generated audio before launch, or does the app need to handle verses with no audio yet?
  4. Donation amounts — are donations free-form (user enters amount) or preset tiers (e.g., $5 / $10 / $25)?
  5. Category structure — how many categories at launch, and does the team have an initial tag list?
  6. COPPA / age gating — given the faith-based audience includes families, is there any under-13 user concern that needs to be addressed?
  7. Analytics tool — PostHog is recommended (GDPR-friendly, self-hostable). Is that acceptable, or does the team have a preference?
  8. Admin users — how many team members need CMS access, and is role-based access needed (e.g., editor vs. publisher)?
  9. Waitlist email flow — beyond the capture, what follow-up cadence is planned? (welcome email only, or a drip sequence?)
  10. AWS account — does the client have an existing AWS account for S3/CloudFront, or should that be provisioned as part of this engagement?
